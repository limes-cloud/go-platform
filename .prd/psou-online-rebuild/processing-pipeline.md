# PanBot 式转存加工链路技术方案

> 状态：待评审
> 日期：2026-10-29
> 范围：`server/psou` 的批量转存、网盘内清洗、批量改名、广告注入、批量分享与任务编排
> 关联文档：`.prd/psou-online-rebuild/README.md`、`pan-account.md`、`search_transfer.md`、`resource.md`
> 2026-10-29 修订：调度链由 `server/cron` 新增子域承载。原方案中的 `processing_job` / `processing_step` 职责收敛到 cron 的 `chain_run` / `chain_node_run`，psou 保留业务案例、文件清单和网盘操作结果。具体见 4.4～4.8。

## 1. 结论

现有 psou 的在线提取本质是“一次同步请求完成：验链 → 转存 → 分享”，适合搜索页的快速提取；PanBot 式能力本质上是“可恢复的多步骤任务”：转存只是第一步，后面还要对**新容器内的副本**做扫描、清洗、改名、广告注入、校验和分享。

不建议把这些步骤直接串进 `/psou/api/search/transfer` 的同步代码里，原因有三个：

1. 链路耗时不可控，文件多或平台限流时会超过 120 秒；
2. 远端删除、改名、上传没有事务，失败后必须知道做到哪一步；
3. 多 App 下需要按应用隔离策略、素材、任务、账号、额度和并发，单次请求模型无法承载。

推荐采用“**cron 调度链 + psou 业务执行**”的架构：

- `cron`：新增任务链子域，负责一次性/定时/手动触发、节点顺序、节点重试、链路取消、收尾节点和运行日志；
- `psou`：负责每一个业务步骤的真实执行，以及来源、账号、临时容器、文件清单、清洗/改名/广告/分享结果；
- MySQL：cron 保存链路运行态，psou 保存业务运行态，两边通过不可变 `run_id` 和 `business_id` 关联；
- Redis：租约辅助、账号锁、同任务互斥、限流和短期进度缓存；
- resource：广告素材、封面、任务清单等对象的统一存储；
- manager：唯一 App 主数据和后台鉴权来源，psou 继续只认 `app` 标识。

一次性调度不采用“拼一个只触发一次的 cron 表达式”。cron 新增长任务链运行表，用 `scheduled_at` 表达一次性触发时间，由 leader 扫描到期运行并推进；`once`、`cron`、`manual` 三种触发方式共用同一套 run 状态机。

## 2. PanBot 公开流程拆解

以下内容依据 PanBot 官方公开教程整理，不涉及对其内部协议或代码的逆向。

### 2.1 标准操作链

PanBot 的核心不是单点功能，而是把多个操作串成一条任务链：

| 阶段 | PanBot 行为 | 关键产物 |
| --- | --- | --- |
| 导入 | 粘贴一条或多条分享链接，支持“名称 + 链接”或仅链接，也支持表格导入 | 待转存来源列表 |
| 识别 | 自动识别百度、夸克等平台 | 平台与来源分享标识 |
| 转存 | 选择目标网盘目录，可同时指定资源分类 | 目标目录中的新副本 |
| 清洗 | 按自定义内容、文件类型扫描广告文件，可先扫描、确认后删除 | 清洗候选清单与删除结果 |
| 改名 | 替换、删除、加前缀、加后缀 | 规范化后的文件/目录名 |
| 广告注入 | 把一个或多个广告文件插入一个或多个目标目录 | 每个目标目录中的广告副本 |
| 分享 | 生成单个合并链接、多个独立链接、子目录链接或目录内文件链接 | 可分发分享链接 |
| 资源化 | 转存和分享结果进入资源管理，可继续复制、编辑、删除、分类和查看数据 | 资源记录与分享记录 |
| 任务化 | 每一批操作都进入网盘任务，记录逐项成功/失败和原因，可重试 | 可追踪、可重试的任务结果 |

官方文档明确支持“批量转存 → 清理广告 → 插入广告 → 批量改名 → 批量分享”连续执行，而不是要求用户逐步手点。这说明其内部至少有“任务 + 步骤 + 条目”三级状态，否则无法呈现逐项结果和失败重试。

### 2.2 各能力的实际语义

**广告清理**

- 操作对象是一个或多个目录。
- 支持自定义扫描内容和文件类型。
- 先扫描出候选文件，再决定是否删除。
- 可配置为“扫描后自动删除”，也可把删除动作留给网盘任务确认。
- 删除有不可逆风险，因此扫描与执行必须分离。

**广告插入**

- 支持一个或多个广告文件。
- 支持一个或多个目标目录。
- 每个目标目录都需要实际写入一份广告文件，不能只在根目录放一次。
- 插入结果按任务逐条记录，失败需要定位到具体目标目录。

**批量改名**

- 规则包括替换、删除指定字符、增加前缀、增加后缀。
- 同时作用于文件和目录。
- 需要处理扩展名保护、非法字符、重名冲突和目录改名后的路径刷新。

**批量分享**

- 单个链接：选中多个文件/目录只生成一个分享。
- 多个链接：每个文件/目录生成一个分享。
- 子目录链接：对每个选中目录继续生成下级子目录分享。
- 目录文件链接：对目录内的文件生成分享。

**任务与资源管理**

- 所有批量动作统一进入任务视图，展示每个条目的成功、失败和失败原因。
- 通过 PanBot 转存/分享产生的链接进入资源管理，可分类、复制、刷新和统计。
- 分享数据一部分取网盘官方数据，一部分通过口令码链路自行记录。

### 2.3 对 psou 的启发

需要补的不是五个孤立接口，而是一套可复用的“网盘文件加工能力”：

- 统一的任务状态机和失败恢复；
- 统一的文件清单快照；
- 文件级清洗、改名、上传、删除能力；
- 可版本化的应用级策略；
- 可审计的分享结果；
- 多 App 下的严格隔离与配额。

## 3. 当前 psou 基线与差异

### 3.1 已有能力

| 能力 | 当前实现 | 可复用程度 |
| --- | --- | --- |
| 账号池 | `pan_account` 按 `app` 隔离，支持百度、夸克、扫码登录、限流、容量 | 直接复用 |
| 转存通路 | `fixed/transfer/search/manual` 四套目录与每日额度 | 直接复用 |
| 来源解析 | `ListShareTree` 支持百度、夸克分享树和转存凭据 | 直接复用 |
| 转存 | `TransferToDir` 支持整包或指定文件 | 直接复用 |
| 目录操作 | `EnsureDir`、`ResolveDir`、`DirStat`、`Exists` | 直接复用 |
| 分享 | `CreateShare` 返回分享链接和分享标识 | 直接复用 |
| 删除 | `Delete`、`DeletePaced` 删除整个容器 | 需扩展为文件级批量删除 |
| 改名 | `RenameFile` 已存在，但未编排成批量规则 | 可复用底层 |
| 上传 | `UploadFile` 支持字符串内容；底层已有分片上传能力 | 需扩展为对象流式上传 |
| 清理 | `search_transfer` 到期清理 worker | 可复用调度思路，不复用数据表 |
| 资源主档 | `resource`、`netdisk` 已有封面、简介、标签、分享链接 | 可直接承接最终结果 |

### 3.2 主要缺口

| 缺口 | 影响 |
| --- | --- |
| 没有任务/步骤/条目模型 | 长任务无法恢复，失败只能整单重来 |
| 转存与分享同步执行 | 批量文件容易超时，无法展示中间进度 |
| 没有文件级递归清单 | 无法预览清洗、改名、注入的目标 |
| 没有文件级批量删除接口 | 只能删整个临时容器，不能在副本内清洗 |
| 没有流式上传对象接口 | 广告图片/视频不宜以字符串或内存整包上传 |
| 没有应用级加工策略 | 多 App 共用一套规则会互相污染 |
| 没有广告素材库 | 素材无法版本化、审计和复用 |
| 没有任务级账号绑定 | 中途换号会导致副本留在旧账号，无法继续加工 |
| 没有“先验证后发布”闸门 | 清洗或分享失败时仍可能暴露半成品链接 |

## 4. 目标架构

### 4.1 逻辑分层

| 层 | 职责 |
| --- | --- |
| 接入层 | 管理端任务/策略/素材接口；公共端快速提取接口；网关鉴权与 Host 解析 |
| 编排层 | 校验请求、固化策略快照、创建任务和步骤、生成幂等键 |
| 执行层 | 按步骤认领任务，调用网盘能力，写回条目状态和检查点 |
| 平台适配层 | 百度、夸克的递归列目录、转存、批量删除、改名、流式上传、分享 |
| 数据层 | MySQL 保存最终状态；Redis 做锁与短缓存；对象存储保存素材和清单 |

### 4.2 部署关系

- `cron` 保留现有 server/client 双进程：server 负责调度链推进，client 负责执行节点。
- `psou` 保持在线 API 服务，不把长任务绑在用户 HTTP 请求上。
- 业务节点通过 cron 的 `http` 执行器调用 psou 内网步骤接口；也可增加专用 `psou` 执行器，但第一阶段不必新造协议。
- cron client 通过节点分组部署；网盘加工节点固定路由到具备内网访问 psou 的 worker 组。
- 一次性 future run 由 cron 落库，不依赖某个 API 实例内存中的 timer。

不建议每个链节点都直接落在 psou API 进程里跑。cron 已经承担 worker 注册、路由、心跳、取消和日志，业务节点的生命周期应复用它，避免再维护第二套执行框架。

### 4.3 核心执行原则

1. **只处理副本**：所有清洗、改名、注入都发生在本次任务新建的临时容器中，永远不直接修改源分享。
2. **先快照后操作**：转存成功后立即生成文件清单，后续步骤以清单为准，不反复全盘扫描。
3. **账号一次绑定**：写入型步骤全部使用同一个账号；中途账号失效时整单失败并换号重跑，不能跨账号续做。
4. **先验证后发布**：分享链接只有在文件完整性、广告注入和命名校验通过后才对外返回。
5. **阶段可恢复**：每一步结束后写检查点；重启后从失败步骤继续，而不是从转存重来。
6. **默认不自动删除**：清洗默认只生成候选清单，自动删除必须由 App 显式开启并经过预览。

### 4.4 cron 新增任务链子域

现有 `task/execution` 继续服务普通定时 HTTP/shell 任务，不改变语义。新增以下表，形成“链定义 → 链版本 → 节点定义 → 运行实例 → 节点实例”五层模型：

| 表 | 作用 | 关键字段 |
| --- | --- | --- |
| `chain` | 任务链逻辑标识 | `app`、`code`、`name`、状态、当前版本、创建人 |
| `chain_version` | 不可变版本快照 | `chain_id`、版本号、触发类型、cron 表达式、并发策略、默认超时、失败策略 |
| `chain_node` | 版本内的节点定义 | `chain_version_id`、序号、节点编码、执行器类型、目标地址、参数模板、重试策略、失败策略、是否收尾节点 |
| `chain_run` | 一次实际运行 | `app`、`chain_id`、`chain_version_id`、触发方式、计划时间、业务关联、状态、当前节点、幂等键、租约 |
| `chain_node_run` | 一个节点的实际执行 | `run_id`、节点定义、尝试次数、状态、worker、日志、开始/结束时间、输入/输出摘要、错误 |

节点日志复用现有 `log`，增加可空的 `chain_run_id`、`chain_node_run_id`、`attempt` 关联字段；普通 task 日志保持原样。

### 4.5 触发模型

| 触发方式 | 实现 |
| --- | --- |
| `manual` | 创建 run 后立即进入待执行 |
| `once` | 创建 run 时写入 `scheduled_at`；leader 扫描到期 run 并推进 |
| `cron` | 保留现有秒级 cron 解析；每次触发创建一个新的 run，不直接执行单个 task |

一次性任务的关键在 `chain_run.scheduled_at`，不使用“某年某月某日只匹配一次”的表达式。这样支持任意未来时间、取消、补跑和幂等，也不会因服务重启时间窗口变化漏触发。

leader 每分钟/每秒扫描不是核心事实源：DB 中 `scheduled_at` 和状态才是。leader 切换后，新 leader 继续扫描，不依赖旧进程内存。

### 4.6 链路推进

第一版只做**线性链 + 收尾节点**，不做任意 DAG：

1. 创建 `chain_run`，状态为 `scheduled` 或 `pending`；
2. 到达触发时间，领取 run，创建第一个 `chain_node_run`；
3. 节点调用 psou 内网步骤接口，成功/失败写回节点实例；
4. 按节点失败策略决定：停止、继续或进入收尾；
5. 成功后创建下一个节点实例，直到链路结束；
6. 终态前执行 `finalizer` 节点，例如清理临时容器、释放锁、写最终分享结果；
7. run 进入 `succeeded`、`partial`、`failed` 或 `canceled`。

DAG、并行分支和条件表达式暂不进入第一版。PanBot 式转存是顺序链，批量并发通过“一来源一 run”获得；过早引入 DAG 会增加调度、取消和补偿复杂度。

### 4.7 与 psou 的职责边界

| 能力 | cron | psou |
| --- | --- | --- |
| 何时触发 | 负责 | 不负责 |
| 链节点顺序与重试 | 负责 | 不负责 |
| worker 选择、心跳、取消 | 负责 | 不负责 |
| 来源分享校验、账号选择 | 不负责 | 负责 |
| 转存、清洗、改名、广告注入 | 不负责 | 负责 |
| 文件清单、清洗明细、素材快照 | 只保存摘要/引用 | 负责完整业务数据 |
| 分享链接 | 只保存结果引用或脱敏摘要 | 负责生成、校验和持久化 |

每个业务节点只接收 `business_id`、`step_code`、`run_id`、`node_run_id` 和幂等键，不由 cron 保存网盘 Token、提取码或完整分享 URL。这样 cron 仍是通用调度组件，psou 的敏感数据不扩散。

### 4.8 节点执行语义

**重试单位**

- 重试单位是 `chain_node_run`，不是整个 task，也不是整条 run。
- 节点失败先按节点重试策略退避；达到上限后再按失败策略终止、跳过或继续。
- 重试沿用同一个 `node_run_id`，只增加 attempt；每次 attempt 对应独立日志，避免重试历史覆盖。
- 重试前调用 psou 的步骤状态接口对账，不能盲目重放删除、改名、上传等远端动作。

**失败策略**

- `stop`：核心节点失败，run 进入失败，随后执行收尾。
- `continue`：非核心节点失败，继续下一节点，最终 run 为 `partial`。
- `skip`：满足条件时跳过节点，记录 `skipped`。
- `finalize`：无论成功、失败或取消都要执行的收尾节点，例如删除临时容器、释放账号锁。

**取消**

- 取消 run 后不再创建新节点；正在执行的节点通过现有 client cancel 机制终止。
- 取消后仍按策略执行 `finalize`，避免临时容器和账号资源泄漏。
- 已经成功的远端副作用不回滚，只记录取消点和收尾结果。

**超时与长任务**

- 每个节点独立配置超时；不得沿用普通 HTTP task 的 30 秒。
- 单节点应执行可在一个超时周期内完成的批次；文件数过大时由 psou 在节点内部拆页并保存游标。
- 第一阶段使用同步节点调用；如果后续出现超过 10 分钟的原子操作，再增加 `202 + callback` 的异步节点，而不是无限放大 HTTP 超时。

**worker 路由**

- 链节点显式指定 worker 组，网盘加工节点只路由到已授权当前 App、且有 psou 内网访问能力的 worker。
- 不同 App 的链可以共用 worker 组，但必须同时受 `worker_app` 授权和 App 级并发配额约束。

## 5. 领域模型

### 5.1 业务案例、条目与清单

调度状态不再在 psou 复制一份。cron 的 `chain_run` 表示一次运行，`chain_node_run` 表示一个步骤；psou 只保存业务上下文和文件级明细：

| 实体 | 作用 | 关键字段 |
| --- | --- | --- |
| `processing_case` | 一次加工业务案例 | `app`、`chain_run_id`、策略版本、模式、来源密文/摘要、平台、绑定账号、目标目录、汇总结果 |
| `processing_item` | 步骤处理到的单个远端文件/目录 | `app`、`case_id`、链节点编码、远端文件标识、操作前后路径、匹配规则、动作、状态、错误 |
| `processing_manifest` | 文件清单快照 | 可落对象存储，记录 case、版本、生成时间和对象 key；DB 只存引用 |
| `processing_event` | 业务审计流水 | App、case、run、node、动作、结果、耗时、错误码、操作者 |

`processing_case.chain_run_id` 是唯一关联键；cron 重试或重新打开节点时，psou 用它做业务幂等。完整文件清单不塞进链路运行表，避免 cron 表变成业务大字段仓库。

### 5.2 策略与素材

| 实体 | 作用 | 关键字段 |
| --- | --- | --- |
| `processing_profile` | App 级加工模板 | `app`、编码、名称、版本、状态、清洗规则、改名规则、注入规则、分享策略、清理策略 |
| `processing_material` | App 级广告素材 | `app`、类型、对象 key、文件名、MIME、大小、内容 MD5、状态 |
| `processing_share` | 运行产生的分享结果 | `app`、case、chain run、账号、平台、范围、远端引用、分享链接密文、过期时间、状态 |

策略在任务创建时固化版本，之后修改策略不影响运行中的任务。禁止在 worker 执行时实时读取“当前最新策略”，否则同一个任务的不同步骤会使用不同规则。

### 5.3 与现有表的关系

- `search_transfer` 继续只服务在线搜索提取和短 TTL 清理，不承载批量加工任务。
- `pan_account` 继续是唯一账号事实源，新增任务不复制 Token。
- `resource`/`netdisk` 继续承接最终资源化结果；加工任务不直接跨模块写这两张表。
- `netdisk` 只接收“已验证成功”的分享结果，不接收中间态临时容器。

## 6. 任务流水线

### 6.1 标准步骤

| 顺序 | 步骤 | 主要动作 | 失败语义 |
| --- | --- | --- | --- |
| 1 | `validate` | 校验 App、来源链接、平台、策略、素材和额度 | 失败即终止，不产生远端副作用 |
| 2 | `snapshot` | 只读拉取源分享树，计算大小、文件数和风险项 | 失败终止，不占转存额度 |
| 3 | `transfer` | 选号、建临时容器、整包或子集转存 | 可换号重试；换号必须重建容器 |
| 4 | `inventory` | 递归读取新容器，生成稳定文件清单 | 失败可重试，不进入清洗 |
| 5 | `clean` | 按规则扫描，生成候选；按策略执行删除 | 删除失败进入部分成功或失败，保留明细 |
| 6 | `rename` | 自底向上执行替换、前后缀和删除字符规则 | 单文件失败可重试或跳过，需检查重名 |
| 7 | `inject` | 按目标目录选择广告素材并上传 | 可配置“强依赖”或“尽力而为” |
| 8 | `verify` | 校验核心文件、目录结构、注入结果和分享前置条件 | 失败禁止发布分享 |
| 9 | `share` | 按单个/多个/子目录/目录文件模式创建分享 | 失败可重试，容器保留 |
| 10 | `publish` | 写分享记录、返回结果、可选通知资源服务 | 失败不回滚网盘，任务可重放 |
| 11 | `cleanup` | 按保留策略删除临时容器或保留为正式目录 | 失败只记录重试，不丢任务线索 |

### 6.2 为什么是这个顺序

- **先转存再清洗**：只操作副本，避免直接删除别人分享中的内容。
- **先清洗再改名**：否则广告文件可能被改名规则改写，导致规则失配。
- **先改名再注入**：注入文件使用固定名，避免被批量改名规则误处理。
- **先验证再分享**：防止出现缺少核心文件、广告注入不完整或目录结构错误的分享。
- **分享成功后再资源化**：没有可分发链接的结果不应成为正式资源。

### 6.3 链路与节点状态

`chain_run` 状态：

| 状态 | 语义 |
| --- | --- |
| `scheduled` | 一次性或定时运行已创建，尚未到触发时间 |
| `pending` | 已到触发时间，等待调度器领取 |
| `running` | 至少一个链节点正在执行 |
| `waiting_retry` | 节点失败，等待下一次节点重试 |
| `partial` | 核心节点成功，但非强依赖节点失败，例如广告注入尽力而为失败 |
| `succeeded` | 全部强依赖节点成功，分享已发布 |
| `failed` | 核心节点失败，不会自动继续 |
| `canceled` | 用户取消，只允许在节点边界停止 |
| `closed` | 收尾节点已执行，按策略保留或清理了临时容器 |

`chain_node_run` 状态：`pending`、`running`、`succeeded`、`failed`、`skipped`、`canceled`。文件和目录级结果在 psou 的 `processing_item` 中记录，不把数万文件状态写进 cron 节点表。

## 7. 关键能力设计

### 7.1 转存与账号绑定

- 批量加工任务使用 `transfer` 通路，不占用在线搜索的 `search` 额度。
- 管理端“指定账号录入资源”继续使用 `manual` 通路。
- 源文件树和预览使用只读验链账号，不检查写入额度。
- 正式转存按平台、剩余容量、每日额度、是否限流、目录是否配置来选号。
- 一旦创建临时容器并发生写入，就把 `account_id` 固定到任务上；后续清洗、改名、注入、分享全部使用该账号。
- 如果绑定账号中途失效，任务不能简单换号继续，因为文件在旧账号。正确做法是标记失败，清理旧容器，重新从第 3 步执行。

### 7.2 清洗规则

清洗规则建议支持以下条件，不在第一阶段引入内容识别：

- 文件名包含/不包含关键词；
- 文件名正则；
- 扩展名白名单/黑名单；
- 文件大小区间；
- 路径包含/不包含；
- 深度范围；
- 是否为目录；
- 用户手工忽略名单。

每条规则包含唯一编码、优先级、动作和置信度。建议动作只有：

- `candidate`：只进入预览，不删除；
- `quarantine`：移动到暂存目录，便于人工确认；
- `delete`：直接删除，必须由 App 策略显式开启。

扫描阶段只读，结果写入 `processing_item`；执行阶段只消费本次扫描结果，不重新计算规则。这样用户看到的预览与实际删除完全一致。

安全边界：

- 只允许处理任务容器内的后代路径；
- 拒绝空文件名、根目录、`..` 路径和超出容器根的操作；
- 目录删除前必须确认其所有子项；
- 规则保存时预编译正则并限制长度；
- 删除前至少保留一份清单，记录原路径、大小、命中规则和操作者。

### 7.3 批量改名

规则顺序固定为：替换 → 删除字符 → 前缀 → 后缀。规则归一化后生成新名称，扩展名默认受保护。

必须处理：

- 非法字符、平台长度限制和中文编码；
- 同名冲突：跳过、自动加序号、覆盖，三种策略显式配置；
- 目录从深到浅改名，子项路径基于新的父路径生成；
- 重试时先按文件标识查当前名称，已是目标名称则视为成功；
- 记录原名称和新名称，支持在分享发布前人工回看。

改名不是“可逆事务”。可以支持将新名称改回旧名称，但删除和覆盖无法保证恢复，因此默认只对临时副本执行。

### 7.4 广告素材与注入

素材管理：

- 素材属于 App，不允许跨 App 复用对象 key；
- 支持文本、图片、短视频等类型，但按白名单控制；
- 上传后记录 MIME、大小、MD5 和对象 key；
- 内容 MD5 相同的素材在 App 内去重；
- 素材删除只做软删除，已有任务仍可按快照读取。

注入规则：

- 选择根目录、每层目录、指定深度目录或路径白名单；
- 一个或多个素材，按顺序复制到目标目录；
- 目标已有同名文件时，按跳过/覆盖/重命名策略处理；
- 只注入任务容器内的目录，不碰账号其他目录；
- 目录数量设置上限，超出后拆成多个子任务；
- 重试前先查目标目录，同名同大小即认为已注入，避免重复文件。

建议注入默认是“尽力而为”，注入失败让任务进入 `partial`，但不阻断分享；如果 App 需要强一致，可以把注入设为强依赖，此时失败会阻断 `share`。

底层能力需要从当前字符串上传扩展为“对象 key → 流式上传到网盘目录”，避免广告视频被整体读入内存。仍复用百度、夸克已有分片上传能力。

### 7.5 分享策略

分享在任务层配置为四种模式：

| 模式 | 说明 |
| --- | --- |
| `single` | 选中多个文件/目录只生成一个链接 |
| `per_item` | 每个选中项生成一个链接 |
| `subdirs` | 每个选中目录继续为下级目录生成链接 |
| `files` | 对目录内文件生成链接 |

约束：

- 单任务分享数量上限可配置，超出后拆子任务；
- 分享 URL 和提取码不写日志、不进普通事件表；
- 分享失败保留容器，允许从 `share` 步骤重试；
- 同任务重试前先查已有分享记录，不能每重试一次就多一个有效分享；
- 分享成功后记录远端分享标识、创建时间、过期时间和所属账号。

### 7.6 幂等与恢复

任务级幂等键由以下信息组成：`app + 来源链接摘要 + 策略版本 + 目标目录/账号 + 业务幂等键`。同一键重复提交返回已有任务，不重复转存。

步骤级恢复必须遵循“先对账、再动作”：

- 转存前记录容器内已有文件；
- 删除前按远端文件标识确认仍存在；
- 改名按当前名称判断是否已完成；
- 注入按目标名称、大小和内容摘要判断；
- 分享按分享范围和已有分享记录判断。

远端操作超时并不等于失败。worker 重启或租约过期后，第一步必须是读取远端现状，而不是立即重放写操作。

### 7.7 失败分类与重试

| 类型 | 处理 |
| --- | --- |
| 网络超时、5xx | 指数退避，最多重试有限次数 |
| 平台限流 | 标记账号限流，切换账号；写入型步骤需整单重跑 |
| 登录态失效 | 账号置失效，任务失败并提示重新登录 |
| 空间不足 | 刷新容量，换账号重跑 |
| 分享失效/提取码错误 | 不重试，直接给用户明确原因 |
| 文件不存在/路径冲突 | 重新读取清单，再决定继续或失败 |
| 规则执行失败 | 记录具体文件，可按策略跳过或终止 |

任务失败不能只返回“转存失败”。对外返回稳定的错误码；内部保留平台原始错误、步骤和文件条目，便于人工定位。

## 8. 多 App 设计

### 8.1 App 来源

- 公共接口用请求 Host 解析 App，沿用现有 manager 解析与缓存链路。
- 管理接口使用 manager 鉴权结果中的 App。
- worker 从任务记录读取 App，再显式构造带 App 的执行上下文。
- 任务请求体、任务查询参数和分享结果都不能覆盖 `app`。

任何查询、更新、删除、锁 key、对象 key 都必须带 App。跨 App 读取任务、素材、分享或账号一律视为越权。

### 8.2 配置隔离

每个 App 独立拥有：

- 加工模板及版本；
- 广告素材库；
- 清洗、改名、注入和分享默认策略；
- 最大并发任务数；
- 单任务最大文件数、目录数、素材数和分享数；
- 临时容器的保留时间和清理策略；
- 可用网盘账号与转存目录。

可以提供“创建 App 时复制系统模板”的能力，但复制完成后各自独立，不能运行时共享一个全局可变策略。

### 8.3 资源隔离

- 对象 key 统一包含 `psou/{app}/processing/...`；
- Redis 锁统一包含 `psou:{app}:processing:...`；
- 链路、运行、节点运行、业务案例、条目和分享表全部以 `app` 作为第一索引维度；
- 同一源链接在不同 App 下是两个完全独立的任务；
- 素材、账号、分享、容量和错误指标都按 App 隔离。

### 8.4 配额与公平性

建议至少限制以下维度：

- 每 App 同时运行的任务数；
- 每账号同时执行的写操作数；
- 每任务文件数、总字节数、目录数；
- 每任务分享数量；
- 每 App 每日新增任务数和对象存储占用；
- 单平台每秒远端操作数，命中限流后自动降速。

调度按 App 做公平轮转，避免一个大租户占满所有 worker。任何单任务超过预算时拆子任务，而不是无限扩大一次任务的执行时间。

### 8.5 App 状态

- App 停用后不再接受新任务；
- 已排队任务不再认领；
- 正在执行的任务在安全边界停止，或允许完成当前步骤后暂停；
- App 删除前必须先清理或移交任务数据，不能留下无主远端容器。

## 9. API 与接入方式

### 9.1 cron 任务链管理接口

新增 `chain` 管理接口，路由保持 cron 现有约定，ID 放 query 或 body，不使用路径变量：

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| GET | `/cron/api/v1/chains` | 任务链列表 |
| GET | `/cron/api/v1/chain` | 任务链及其当前版本 |
| POST | `/cron/api/v1/chain` | 创建任务链 |
| PUT | `/cron/api/v1/chain` | 创建新版本，不修改运行中版本 |
| DELETE | `/cron/api/v1/chain` | 删除未被运行引用的链路 |
| POST | `/cron/api/v1/chain/run` | 手动或指定未来时间创建 run |
| GET | `/cron/api/v1/chain_runs` | 按 App、链路、状态、时间查询运行 |
| GET | `/cron/api/v1/chain_run` | 查看运行、节点实例、日志和汇总 |
| POST | `/cron/api/v1/chain_run/action` | 取消、重试失败节点、重新打开链路 |
| PUT | `/cron/api/v1/chain/status` | 启用/停用链路触发 |

`POST /cron/api/v1/chain/run` 的请求包含：链路编码、触发类型 `manual|once`、计划时间、业务幂等键、业务引用 `business_id`。cron 只保存业务引用，不保存来源分享凭据。

批量提交多个来源时，由调用方为每个来源创建一个 run，并共用一个批次标识。不要把一个批次做成一条串行链，否则一个来源失败会阻塞其他来源。

### 9.2 psou 业务接口

psou 保留加工模板、素材和业务案例接口：

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| POST | `/psou/admin/processing/profiles` | 创建加工模板 |
| PUT | `/psou/admin/processing/profiles` | 创建新版本或更新非运行态模板 |
| GET | `/psou/admin/processing/profiles` | 模板列表 |
| GET | `/psou/admin/processing/profile` | 模板详情 |
| POST | `/psou/admin/processing/materials` | 登记广告素材 |
| GET | `/psou/admin/processing/materials` | 素材列表 |
| POST | `/psou/admin/processing/cases` | 为 run 创建业务案例 |
| GET | `/psou/admin/processing/cases` | 案例列表与汇总 |
| GET | `/psou/admin/processing/case` | 案例、清单、文件条目和分享结果 |
| POST | `/psou/admin/processing/cases/preview` | 只读扫描与干跑 |
| GET | `/psou/admin/processing/shares` | 分享记录与状态 |

psou 另提供仅供 cron worker 调用的内网步骤接口。该接口必须校验内网来源或内部签名，不能经由公网网关暴露：

| 方法 | 内部路径 | 用途 |
| --- | --- | --- |
| POST | `/internal/psou/processing/step` | 执行一个链节点对应的业务步骤 |
| POST | `/internal/psou/processing/step/status` | 节点重试前对账当前业务状态 |
| POST | `/internal/psou/processing/step/finalize` | 清理临时容器、释放业务资源 |

步骤请求只传 `app`、`business_id`、`run_id`、`node_run_id`、`step_code` 和调用幂等键。psou 根据业务案例中的策略快照执行，不信任 cron 传来的标题、链接、账号或文件清单。

### 9.3 公共端

现有 `/psou/api/search/transfer` 建议保持不变，继续承担“无需加工、快速提取”的场景。新增异步加工能力时：

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| POST | `/psou/api/search/transfer/job` | 按 App 默认加工模板创建业务案例和 cron run |
| GET | `/psou/api/search/transfer/job` | 查询链运行进度和最终分享 |

迁移策略：

1. 先让管理端批量任务使用新任务引擎；
2. 稳定后再为公共页提供异步模式；
3. App 可通过配置选择快速同步模式或异步加工模式；
4. 两种模式共用平台能力和账号池，但数据表与超时语义分开。

不建议直接把现有同步接口改成异步，否则老客户端会在无感知的情况下拿到任务 ID 而不是分享链接。

### 9.4 资源化

任务成功后可返回结构化结果：

- 平台、账号、源链接摘要；
- 目标目录和临时容器引用；
- 最终文件数、目录数、总大小；
- 清洗删除数、改名数、注入数；
- 分享列表、过期时间和分享标识；
- 警告和非核心失败清单。

管理端可继续走现有 `netdisk` 保存流程。后续如果需要自动创建资源，应通过明确的应用服务或事件出口完成，不能让 worker 直接写 `resource`/`netdisk` 表。

## 10. 数据、安全与审计

### 10.1 敏感数据

- 网盘 Token 继续只存在 `pan_account`，任务表不复制。
- 批量任务需要重试来源链接，因此来源 URL 和提取码必须加密存储；密钥由环境变量注入，缺失时拒绝创建任务。
- 分享链接包含提取码，按敏感字段处理；列表返回给有权限的 App 管理员，不写日志和错误信息。
- 广告素材对象 key 不作为公开 URL 直接暴露，worker 通过内部读取能力获取内容。

### 10.2 审计

每个任务至少记录：

- 谁在哪个 App 创建；
- 使用了哪个账号、模板版本和素材版本；
- 每一步开始/结束时间、重试次数和结果；
- 删除、覆盖、改名等高风险动作的完整清单；
- 最终分享链接和发布状态。

审计记录不随临时容器清理而删除。

### 10.3 保留策略

- 成功任务和分享记录保留较长时间，便于追踪；
- 失败任务保留到人工处理完成；
- 文件清单可放对象存储，按任务保留；
- 临时容器按 App 策略清理，清理失败进入人工处理队列；
- 已清理任务保留摘要，不保留可恢复的敏感凭据。

## 11. 可观测性

建议按 App 监控：

- 队列深度、运行中任务数、平均等待时间；
- 各步骤成功率、P95/P99 耗时；
- 转存、删除、改名、上传、分享调用量；
- 平台限流、账号失效、空间不足次数；
- 清洗删除数、注入失败数、分享失败数；
- 清理积压和清理失败容器数。

日志统一带 `app`、`chain_run_id`、`chain_node_run_id`、`business_id`、`platform`、`account_id`，但不带 Token、提取码和完整分享 URL。

## 12. 实施顺序

### 阶段一：cron 任务链底座

- 新增 `chain`、`chain_version`、`chain_node`、`chain_run`、`chain_node_run` 表；
- 保持现有 `task/execution` 行为不变，新增链路 API 与运行实例；
- 支持 `manual`、`once`、`cron` 三种触发，一次性任务落 `scheduled_at`；
- leader 扫描到期 run，节点按顺序推进；
- 实现节点级重试、失败策略、取消、收尾节点和链路日志；
- 增加 App 级并发、单链路最大节点数和 worker 分组路由；
- 用纯 HTTP 节点验证一次性 run、重启恢复、取消和 leader 切换。

### 阶段二：psou 业务步骤与转存

- 新增 `processing_case`、`processing_item`、清单和分享表；
- 新增 psou 内网步骤接口和业务幂等；
- 从现有 `Search` 抽出可复用的源树、选号、转存和分享编排；
- 只实现 `validate → snapshot → transfer → verify → share → publish`；
- 用少量百度、夸克真实分享验证链路断点恢复和账号绑定。

### 阶段三：文件加工

- 扩展 `PanClient`：递归列目录、文件级批量删除、流式上传；
- 实现文件清单快照；
- 实现清洗扫描、预览和执行；
- 实现批量改名；
- 实现广告素材和注入；
- 从管理端提供完整干跑能力。

### 阶段四：批量分享与资源化

- 四种分享模式；
- 任务结果转资源、写分享记录；
- 分享状态刷新；
- 失败和部分成功在管理端可视化。

### 阶段五：公共端与扩展

- 公共提取按 App 切换异步加工；
- 自动同步/追更作为独立调度模块；
- 跨盘互传、播放、链接统计等按优先级另行设计。

## 13. 验收标准

### 基础正确性

- 同一幂等键重复提交不会重复转存；
- worker 重启后能从失败步骤恢复，不重复删除或注入；
- 源分享取消、提取码错误、账号失效、空间不足能返回稳定错误；
- 分享生成前一定能看到文件数、大小和关键步骤结果。

### 文件加工

- 清洗预览与最终删除清单完全一致；
- 删除失败能定位到文件，未命中规则的文件不被误删；
- 改名正确处理扩展名、非法字符、重名和目录层级；
- 广告注入重复执行不会产生重复文件；
- 注入失败按 App 策略进入 `partial` 或阻断分享。

### 多 App

- 两个 App 使用同一来源链接时产生独立任务和独立容器；
- 跨 App 查询任务、素材、分享、账号全部失败；
- worker 不会认领已停用 App 的新任务；
- 一个 App 的大批量任务不会耗尽其他 App 的并发额度；
- 对象路径、Redis key、日志和指标都能明确区分 App。

### 运营与可维护性

- 任务列表能看清每个来源、步骤和失败原因；
- 失败任务可重试，取消任务不会留下无记录的远端容器；
- 清理失败不会直接丢记录；
- 管理端能按 App 查看容量、限流和任务积压。

## 14. 风险与取舍

| 风险 | 处理 |
| --- | --- |
| 远端删除不可逆 | 默认预览、白名单、只操作临时副本；高风险动作保留清单 |
| 远端写操作超时但实际成功 | 所有重试先读取现状，再做动作 |
| 账号中途失效 | 写入步骤绑定账号，失败后整单换号重跑 |
| 大批量任务拖垮在线接口 | 有界 worker、App 配额、任务拆批、独立 worker 部署 |
| 规则误伤正常文件 | 规则版本化、干跑、手工忽略名单 |
| 广告影响资源可信度 | 按 App 配置、分层展示、允许关闭、保留注入审计 |
| MySQL 5.7 无 `SKIP LOCKED` | 用条件更新抢任务、租约和心跳，不依赖 8.0 特性 |
| 策略变更影响运行任务 | 任务固化策略版本，不读取最新配置 |
| cron 与 psou 双状态不一致 | cron 只存调度态，psou 只存业务态；以 `chain_run_id`、`node_run_id` 和业务幂等键对账 |
| 一次性触发漏执行 | `scheduled_at` 落库，leader 扫描；不依赖内存 timer |
| cron 运行表被文件明细撑大 | 文件清单落对象存储，DB 只存引用；条目留在 psou |
| 单节点 HTTP 超时 | 节点内部拆批；配置独立节点超时；第一阶段不做跨请求异步回调 |
| 多 App 抢占 worker | `worker_app` 授权 + App 并发配额 + 分组路由 |

## 16. 最终建议

最合适的落地方式不是把 PanBot 的每个按钮照搬成同步接口，而是把 `cron` 扩展成通用任务链调度中心，psou 专注业务步骤：

1. cron 新增 `chain_run/chain_node_run`，解决一次性触发、链式推进、节点重试、取消和收尾；
2. psou 新增 `processing_case/processing_item`，解决业务步骤、文件清单、账号和分享；
3. 用 `scheduled_at` 表达一次性运行，不用伪 cron 表达式；
4. 第一版只做线性链 + finalizer，不做 DAG；
5. 用临时容器和“先验证后发布”解决远端操作不可逆；
6. 用现有账号池、转存通路和 `PanClient` 解决平台差异；
7. 先管理端干跑和小流量真实联调，再逐步开放公共端。

这样后续增加批量分享、自动同步、跨盘互传或分享数据统计时，都可以复用同一套链定义和运行模型，而不需要再次改造转存主流程。
