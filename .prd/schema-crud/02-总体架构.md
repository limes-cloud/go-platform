# 02 总体架构

## 1. 核心思想：编译，不是渲染

**不新建渲染组件树。** `ArtTable` / `ArtSearchBar` / `ArtForm` / `ArtOperation` 已经是数组驱动，再包一层递归渲染器只是把 props 换个名字。

我们要做的是**一个编译器**：把「模型配置」编译成这四个组件已经认识的 props。

```
ModelSchema（一份模型配置）
      │
      │  compile()  ← 纯异步函数，产物是可缓存、可序列化的纯数据
      ↓
Compiled {
  meta,                      // 页面元信息（标题、openMode、默认展开搜索项数…）
  form:    FormItem[],       // → ArtForm
  search:  SearchFormItem[], // → ArtSearchBar
  columns: ColumnOption[],   // → ArtTable
  actions: OperationItem[],  // → ArtOperation
  toolbar: ToolbarButton[],  // → ArtTableHeader #left
  api:     ApiFnSet,         // → useTable.core.apiFn 等
}
      ↓
GenericCrudPage.vue（通用页壳，普通 props 传递）
```

关键约束：**编译是独立的纯函数，不在渲染组件里边渲染边推导场景。** 产物必须可缓存——外键字典预取有网络开销，不能每次开弹窗重编译。

## 2. 四阶段编译流水线

移植 alien-form 的 `SchemaCompiler.compile()`（`packages/shared/src/compiler/SchemaCompiler.ts:81-108`），职责切分很干净：

```ts
export async function compile(schema: ModelSchema, opts: CompileOptions = {}): Promise<Compiled> {
  const store: Record<string, unknown> = {}          // 单次编译的共享缓存
  const errors: CompileError[] = []

  // ① prefetch —— 深度遍历收集所有 plugin marker，并发预取远程字典进 store
  //    跨三个场景只做一次（这是把 store 放在 compile 内而非模块级的原因）
  await prefetch(schema, plugins, { schema, store, request, errors })

  // ② resolve —— 每个场景各拿一份深拷贝，独立解析 marker，互不污染
  const shared = { store, request, errors }
  const [formTree, searchTree, tableTree] = await Promise.all([
    resolveScene(cloneSchema(schema), 'form',   shared),
    resolveScene(cloneSchema(schema), 'search', shared),
    resolveScene(cloneSchema(schema), 'table',  shared),
  ])

  // ③ project —— 场景结构变换（分组/摊平/取顶层列）
  // ④ descriptor —— 字段级三场景语义，在 project 内部按字段调用
  return {
    meta:    schema.meta,
    form:    projectForm(formTree, ctx),
    search:  projectSearch(searchTree, ctx),
    columns: projectColumns(tableTree, ctx),
    actions: compileActions(schema.actions, ctx),
    toolbar: compileToolbar(schema.toolbar, ctx),
    api:     compileApi(schema.api, ctx),
    errors,                                          // 不抛异常，收集后交给错误面板
  }
}
```

| 阶段 | 职责 | 为什么独立 |
|---|---|---|
| ① prefetch | 收集 marker，并发预取远程数据 | 三场景共用同一份字典，只拉一次 |
| ② resolve | 各场景独立解析 marker | 同一个 marker 在不同场景解析成不同东西（见 [06](06-数据源与插件.md)），必须隔离 |
| ③ project | 结构变换：分组 / 摊平 / 取顶层 | 三场景的**结构**规则不同（见 [05](05-场景投影.md)） |
| ④ descriptor | 一种字段类型的三场景语义 | 加字段类型只改一处（见 [04](04-字段描述符.md)） |

**`store` 必须是单次编译作用域，不能是模块级缓存**——否则跨模型串数据。

## 3. 两条渲染路径的分界（务必先确定）

这是 alien-form 摸对了但没写进文档的一条分界，我们要显式确定：

```
表单 / 搜索 / 详情 ──→ 配置 → 表单运行时（值、校验、联动） → 字段组件
表格             ──→ 配置 → 直接渲染字段组件（只读态），✗ 不经过表单运行时
```

**理由**：一行一个表单实例的开销无法接受。alien-form 的 `Table.tsx` 就是直接 `fieldComponents[column.component]` 手动实例化，绕开整个 form runtime。

**两条路共享的是「字段组件」和「组件注册表」，不共享运行时。**

收益：「Select 在表格里显示 label 而不是 value」这件事只需在字段组件里写一次（判 `mode === 'detail'`），不必为每列单独写 formatter。我们统计里那 7 处枚举查表 formatter + 6 处 ElTag 插槽，本质都在重复这一件事。

## 4. 两层配置：JSON 是 TS 的严格子集

纯 JSON 覆盖不到全部页面（约 22~26 / 49，见 [00](00-背景与目标.md)），但 JS/TS 无法被服务端安全下发（下发即 RCE）。所以分层，**且不是两套平行系统**：

| | 第一层：TS 配置模块 | 第二层：JSON |
|---|---|---|
| 位置 | `src/views/**/*.crud.ts`，编译进包 | 后端 `page_schema` 表，运行时下发 |
| 函数 | 随处可用 | **不允许** |
| 覆盖 | 49 / 49 | 约 22~26 |
| 类型安全 | **TS 全程检查** | JSON Schema 运行时校验 |
| 新增 App | 需前端发版 | **在线配置即可** |

```
JSON（无函数子集）
   │  fromJSON()  ← 把声明式规格翻译成函数值字段
   ↓             （format:'datetime' → formatter: r => formatTime(...)）
CrudConfig（TS 类型，函数已就位）
   │  compile()
   ↓
Compiled → GenericCrudPage
```

**同一个运行时、同一个类型、同一个页壳。** 由此得到三个性质：

1. **可升级**：某页 JSON 写到表达不了了，直接改成 `.crud.ts`，不用重写
2. **`@handlerName` 逃生口**：JSON 里引用注册表中的具名函数，配置本身仍可序列化（见 [07](07-联动与表达式.md)）
3. **顺序更稳**：先做第一层用 TS 验证配置形状，再抽第二层冻结 JSON 契约和数据库表——TS 结构改起来编译器会告诉你所有受影响的地方，JSON 契约一旦发布就很难改

**类型安全这一点的实证依据**：现有代码里 8 类死配置（`:show-button="false"` 27 处、`suffix` 5 处、`show:` 函数 1 处、`type:'input-number'`、`type:'host'` rule、二维数组 formItems……）**全部**是「配了但组件不认」。TS 会在 IDE 里当场标红；JSON Schema 只能抓一部分且要等运行时。详见 [13](13-既存缺陷修复.md)。

## 6. 通用页壳的两种接入方式

**方式 A：纯配置驱动，零 `.vue` 文件**

后端菜单填 `component: '/generic/crud'`，`registerRoutes.ts:16` 的 `import.meta.glob('../../views/**/*.vue')` 自动命中 `src/views/generic/crud/index.vue`；schema key 从路由 `meta` 或 `query` 取。**菜单侧零改动。**

**方式 B：需要本地组件/插槽时，页面仍存在但只有 10 行**

```vue
<!-- src/views/manager/role/index.vue -->
<template>
  <GenericCrudPage :config="config">
    <template #after><Menu ref="menu" /></template>
  </GenericCrudPage>
</template>
<script setup lang="ts">
  import config from './role.crud'
  import Menu from './menu/index.vue'
</script>
```

方式 B 是让那 10~13 个「只差一两处函数」的页面能进引擎的关键。

## 7. 与现有组件的关系

编译目标全部是已核实的现有契约，**不改组件**（[13](13-既存缺陷修复.md) 的缺陷修复除外）：

| 编译产物 | 消费方 | 契约要点 |
|---|---|---|
| `ColumnOption[]` | `ArtTable` | `useSlot`+`slotName` 具名插槽；`formatter(row)` 可返回 VNode；`[key:string]: any` 直通 el-table-column |
| `SearchFormItem[]` | `ArtSearchBar` | v-model 表单数据，emits `search`/`reset` |
| `FormItem[]` | `ArtForm` | `rules` 取自 `item.props.rules`；`v-bind="getProps(item)"` 整包透传；`getNestedValue` 支持任意深度 `a.b.c`；**每项另有具名插槽 `#[item.key]`** |
| `OperationItem[]` | `ArtOperation` | 内置 `hasPermission()` 过滤 + `popConfirm`；>2 项自动折叠 dropdown |
| `ApiFnSet` + 分页 | `useTable` | `core.apiFn` 接受任意函数；分页字段映射兜底在 `src/utils/table/tableConfig.ts` |

**`ArtForm` 的具名插槽 `#[item.key]` 是一个现成的、被现有代码 0 使用的逃生口**——通用页壳可以把它暴露成 `<template #field-xxx>`，用于极少数需要完全自定义某个表单项的场景，无需改 `ArtForm`。
