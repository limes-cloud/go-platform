# 11 错误与可观测

## 1. 核心原则

配置驱动系统里，**配置写错是常态**，不是异常。所以：

1. **绝不白屏** —— 校验失败渲染可归因的错误面板，不是空页面
2. **绝不静默降级** —— 类型名未命中、handler 未注册、字段引用不到，一律告警，不 fallback 到「看起来能用」
3. **错误可归因** —— 必须能定位到「哪个字段的哪条规则」
4. **单点错误不炸全页** —— 一列/一个表单项出错只降级该项

第 2 条是从现有 bug 里学到的：`art-form/index.vue:316` 的 `|| componentMap['input']` 让 6 种字段类型静默降级成文本框，在生产跑了很久没人发现（见 [13](13-既存缺陷修复.md)）。

## 2. 错误对象

借 alien-form `core/src/types.ts:226-241` 的 `FormError` 形状，`scope` 是关键——它让配置界面能直接高亮出错位置。

```ts
type ErrorScope =
  | 'schema'        // JSON Schema 元校验失败
  | 'component'     // 组件类型未注册
  | 'api'           // ApiSpec 无法解析 / 引用的 apiFn 未注册
  | 'dataSource'    // 选项来源解析失败
  | 'plugin'        // 未注册的 plugin marker
  | 'reaction'      // 联动规则非法
  | 'expression'    // 表达式语法错误
  | 'handler'       // @handler 未注册
  | 'validator'     // 校验规则非法（含 async-validator 不认的 type）
  | 'format'        // FormatSpec / SlotSpec 非法
  | 'action'        // 行操作声明非法
  | 'auth'          // 权限码不存在（警告级）
  | 'json'          // jsonFields 解析失败

interface CompileError {
  scope: ErrorScope
  level: 'error' | 'warn'
  path?: string          // 字段路径，如 'setting.jwt.secret'
  key?: string           // 规则键，如 'x-reactions[0].when'
  message: string
  cause?: unknown
}
```

## 3. 三道防线

### 第一道：JSON Schema 元校验（仅第二层 JSON）

保存时 + 运行时加载后各校验一次。

```ts
const result = validateModelSchema(json)   // ajv，dev 环境必开，prod 环境也开（成本可忽略）
if (!result.ok) return renderErrorPanel(result.errors)
```

**必须避免 alien-form 的坑**：它有一份 `alien-form-schema.json`（12KB draft-07 元定义），但

- 全仓库**零消费方**（没有 ajv/zod 依赖，`.vscode/settings.json` 也没有 `json.schemas` 映射），只是个悬空产物
- **已与代码不同步且是危险的不同步**：两处 `additionalProperties: false`，却缺了 `x-layout` 和 `x-effect` → 按它校验，所有带布局分组的真实 schema 都会报错
- 它约束的是 core 协议，而服务端下发的是 CMS 协议，**两者根本不是一个东西**

我们的要求：**JSON Schema 与 `types.ts` 同源**。方案是从 TS 类型生成（`ts-json-schema-generator`），或反过来由 JSON Schema 生成 TS 类型。**不允许手工维护两份。** 这一项进 CI 检查。

### 第二道：编译期收集

`compile()` **返回错误不抛异常**：

```ts
interface Compiled {
  meta: ModelMeta
  form: FormProjection
  search: SearchFormItem[]
  columns: ColumnOption[]
  actions: ActionItem[]
  toolbar: ToolbarButton[]
  api: ApiFnSet
  errors: CompileError[]       // ← 单点错误在这里，页面仍可渲染
}
```

降级策略：

| 出错位置 | 降级行为 |
|---|---|
| 单个字段的组件类型未注册 | 该字段渲染为 disabled 的占位输入框 + 红框提示 |
| 单个列的 `format`/`slot` 非法 | 该列渲染原始值 |
| 单条 `x-reactions` 非法 | 该条不生效，其余联动照常 |
| 单条 rule 非法 | 该条不生效，其余校验照常 |
| **`api.list` 无法解析** | **整页降级**（没有数据源页面无意义），渲染错误面板 |
| **JSON Schema 校验失败** | **整页降级** |

分界：**数据源和整体结构错 → 整页降级；字段级错 → 局部降级。**

### 第三道：运行时通道

```ts
const { compiled, errors, onRuntimeError } = useCrudSchema(schemaRef)
onRuntimeError((e: CompileError) => { /* 上报 + dev 环境 console.error */ })
```

运行时错误来源：`@handler` 执行抛异常、`$row.xxx` 解析不到、`jsonFields` 解析失败、`dependsOn` 请求失败。

**handler 抛异常必须被捕获进错误通道，不炸页面**（alien-form 这点做对了：`form.ts` 里 reaction 的内联函数异常被捕获进 onError）。

## 4. 错误面板

开发环境和生产环境行为不同：

| | 开发环境 | 生产环境 |
|---|---|---|
| `level: 'error'` | 页面顶部醒目面板，列出全部错误（scope / path / key / message） | 同样显示面板，但文案对用户友好（「页面配置存在问题，请联系管理员」+ 折叠的技术详情） |
| `level: 'warn'` | 面板内可折叠区 + `console.warn` | 仅上报，不打扰用户 |
| 整页降级 | 错误面板 + 原始 JSON（monaco 只读，行号对应 `path`） | 错误面板 + 「返回」按钮 |

项目已有 `monaco-editor` 和 `ArtCodeEditor`，错误面板里展示原始 JSON 并定位到出错行是低成本的。

## 5. 组件类型未命中的处理（重点）

这是最容易出错、也最容易被静默吞掉的一类。三层保护：

```ts
export function resolveComponent(name: string, ctx: ProjectCtx): ComponentName | null {
  // ① 归一化：小写 + 去连字符/下划线，吸收 inputNumber / input-number / input_number
  const norm = name.toLowerCase().replace(/[-_]/g, '')
  const hit = componentAliasMap[norm]
  if (hit) return hit
  // ② 未命中：进错误通道，不 fallback
  ctx.errors.push({ scope: 'component', level: 'error', path: ctx.path,
    message: `未注册的组件类型 "${name}"。可用类型：${Object.keys(registry.components).join(', ')}` })
  return null
}
```

三层：**归一化吸收大小写与分隔符差异 → 未命中报错 → 绝不 fallback**。

`componentAliasMap` 从 `registry.components` 自动生成（每个 key 的归一化形式 + `defaults` 里声明的别名），不手工维护。

## 6. 可观测性（本期最小集）

不做完整埋点，只做三件低成本的事：

1. **编译耗时**：`compile()` 记录耗时，超过阈值（比如 500ms）warn。外键预取是主要开销，这个指标能暴露「某页配了 10 个远程选项」
2. **错误上报**：`level: 'error'` 的 `CompileError` 上报到现有日志通道（若无则先 `console.error`）
3. **schema 版本标记**：页面渲染时把 `schemaId + version` 挂到 DOM `data-*` 属性，出问题时能一眼看出用户当时用的是哪版配置

## 7. 与现有错误处理的关系

不改动 `src/utils/http/index.ts` 的响应拦截器（业务 `code` 判定、401 refresh token 队列重放、失败弹窗）。

分工：**HTTP/业务错误走现有拦截器（面向用户），配置错误走本文档的通道（面向配置维护者）。** 两者不混。
