# 01 技术选型

## 结论

**自研配置编译器 + 复用现有 `art-*` 组件。不引入任何第三方 schema 引擎。**

但**吸收 alien-form 的编译器架构**（四阶段流水线 + 字段描述符 + 受限表达式引擎）和 **Formily 的联动协议形状**（`x-reactions`）。借设计，不装依赖。

## 候选评估

### Formily（`@formily/vue` + `@formily/element-plus`）— 否

三条决定性理由：

**① 官方明确不提供列表页方案。** `alibaba/formily` 的 `docs/guide/scenes/query-list.zh-CN.md` 全文 49 行只有伪代码，原文：

> 目前 Formily 还没想好怎么既考虑通用性又能考虑业务快速上手，**所以暂时不开放出具体组件**。

它给的是 `ArrayTable`（表单内可编辑数组，无分页无服务端排序）、`FormDialog`/`FormDrawer`、`FormStep`/`FormTab`、`PreviewText`。而我们需要的表格、分页、列显隐持久化、行操作、按钮权限、批量操作、请求编排——**一个都不给**，且这些我们的 `art-table` / `useTable`（699 行）/ `ArtOperation` / `usePermission` 已经有了。

引入它换不到列表能力，只换来把能用的 `ArtForm` 重写一遍。**投入产出方向是反的。**

**② 唯一的 Element Plus 适配层停更两年，且与主题体系冲突。**

| 包 / 仓库 | 版本 | 最后活动 | 月下载 |
|---|---|---|---|
| `@formily/element-plus` | **1.1.0**（已核实 npm） | **2024-07-05** | 3,267 |
| `@formily/vue` | **2.3.7**（已核实 npm） | 2025-05-15 发布 | 7,511 |
| `@formily/react` | 2.3.7 | — | 122,694 |
| `alibaba/formily` 主仓 | — | 2025-06-21 | — |
| `alibaba/designable` | 1.0.0-beta.45 | **2022-04-25** | — |

具体问题：它的 `Form`/`FormItem` **不包装 `ElForm`/`ElFormItem` 而是自己重写**（`FormItem` 576 行 TS + 518 行自带 SCSS），会和 art-design-pro 的表单样式/暗色主题打架；`element-plus: ^2.4.0` 与 `@element-plus/icons-vue: ^1.1.1` 被放进 **dependencies 而非 peerDependencies**（我们是 `^2.11.5` + `^2.3.2`，icons 会多装一份 v1）；还拖 `vuedraggable`、`vue-slicksort`、`resize-observer-polyfill`。

它在 `formilyjs` 组织下、maintainer 与内核同批人，但**不在官方文档里**——主仓 docs 全文 grep `element-plus` 命中 0 次，官方快速开始只列 `@formily/antd` 和 `@formily/next`；其 README 是从 antd 版复制的，正文仍写着 "Integrated Alibaba Fusion and Ant Design components"。

**③ `{{ }}` 表达式默认走 `new Function` + `with`。** `packages/json-schema/src/compiler.ts:26`：

```js
new Function('$root', `with($root) { return (${expression}); }`)(scope)
```

在「服务端下发配置」这个前提下，等于把浏览器端任意代码执行权交给配置编辑者。官方有 `registerCompiler()` 可换受限求值器，但默认不安全，而我们的场景正是让非前端人员在线改配置。

**补充风险**：Vue3 响应式桥接靠劫持组件实例私有 API（`packages/reactive-vue/src/hooks/useObserver.ts` 里 `Object.defineProperty(vm, 'effect', ...)`），更新粒度是 `$forceUpdate()` 整组件重渲染。Vue 3.6 已到 rc.6，而 `@formily/vue` 最后发布 2025-05-15，无 3.6 验证。

包体积不是问题（`@formily/vue` 全依赖树 39.7 kB + 适配层约 33 kB ≈ 60~75 kB gzip），**所以体积不是拒绝理由，生态与方向才是**。

### amis（百度）— 否

功能最完整（CRUD/表格/分页/权限/弹窗全有），有可用的 `amis-editor`，`baidu/amis` 活跃。但**它是 React**。

官方 `docs/zh-CN/start/getting-started.md` 的「vue」一节全文一句话：基于 SDK 封装成 component，示例指向 `aisuda/vue2-amis-demo`（Vue **2**，最后提交 2024-11-05）；**没有官方 vue3 示例仓库**。实际落地是在 Vue 应用里塞一整个 React 运行时（或走 veaury 桥，社区有 `renderer with name X has already exists` 类报错记录）。样式命名空间与 element-plus 割裂，我们的 `art-*` 组件与 amis 渲染器互不可见。

体积：SDK `sdk.js` 547 kB + `sdk.css` 300 kB gzip。

**定位判断**：适合新开一个独立的低代码子系统，不适合改造存量 art-design-pro 页面。

### form-create（`@form-create/element-ui`）— 暂不，但列为 plan_b

社区方案，活跃度远超 Formily 的 element-plus 适配层：3.3.3（2026-08-06 发布），月下载 **54,616**（约 16 倍），配套 `@form-create/designer` 3.5.0，原生 Element Plus。

但它**同样只管表单不管列表**，覆盖不到我们 80% 的工作量。

**列为 plan_b 的条件**：若自研编译器在表单联动 / 异步选项 / 数组字段上复杂度失控，下一步评估 form-create——**不是回头看 Formily**。

### alien-form — 不直接用，但抄架构

`/Users/fangweiye/software/alien-form`。它做了 Formily 明确拒绝做的那块：`SchemaCompiler.compile()` 一次产出 `{ form, filter, columns }`，即「一份模型投影出三个场景」。

不能直接用的原因：

- **未发布到 npm**（`@alien-form/core` registry 404），git 历史只有 1 个 squash commit（2026-08-24）
- `packages/react`（753 行）+ `packages/shared`（3228 行场景组件）是 React + antd，全部要重写
- **README / docs / CHANGELOG 三份文档全部落后于至少一次大重构**：README 宣传 6 种场景（含移动端卡片），代码里 `Scene = "form" | "filter" | "table"` 只有 3 种（已核实 `packages/shared/src/compiler/types.ts:7`）；`docs/scene-driven-architecture.zh-CN.md` 整篇 233 行描述的 API 全部不存在
- 我们最想抄的 `compiler/`（1169 行）**零测试**

**但它的 `compiler/` 目录我已核实零 React import，纯 TypeScript 纯函数**——可以整段移植。详见 [02-总体架构](02-总体架构.md)。

## 横向对比

约束：Vue 3 + Element Plus 存量后台（85 view / 21928 行）、需服务端下发配置、需按钮级权限。

| | Formily + element-plus | amis | form-create | 自研编译器 |
|---|---|---|---|---|
| 框架契合 | Vue3，但适配层重写 FormItem，主题冲突 | **React**，需挂 React 运行时 | Vue3 原生 | 完全契合 |
| CRUD 覆盖 | 仅表单（官方明确不给列表） | **完整** | 仅表单 | 由我们决定 |
| 服务端下发 | 支持，但 `new Function` 不安全 | 支持 | 支持 | 支持 |
| 可视化设计器 | Vue 侧是空壳包 | **可用** | 有 | 无（本期不做） |
| 增量体积 gzip | 60~75 kB | **850 kB 起** | ~40 kB | 5~15 kB |
| 维护风险 | 适配层 2 年无更新 | 活跃 | 活跃 | 自己背 |
| 复用现有 `art-*` | 每个要 `transformComponent` + `mapProps` 包一层 | 基本不能 | 部分 | **直接复用** |

## 明确不抄

| 不抄什么 | 理由 |
|---|---|
| alien-form 的 signal 化字段树（1150 行，每字段 14 个 signal + 扁平 fieldsMap + 四种节点 + mount/unmount 生命周期） | 它在费力模拟 Vue 的 `reactive` + `computed` 免费提供的东西 |
| `x-format` 输入输出格式化管道 | 存在原因是它自伤的限制：叶子只能存 `string\|number\|boolean`（`form.ts:74-82` 直接 throw），导致多选值必须 JSON 字符串桥接。Vue 里数组就是数组 |
| `definitions` + `$ref` + 循环引用检测（76 行 + 203 行测试） | 后台 CRUD 模型间几乎无递归复用需求；真要复用编译期浅合并即可 |
| `x-effect`（字段挂载副作用 + disposer） | 声明式配置里塞命令式副作用，难调试难测试易泄漏 |
| `decorator` / `decoratorProps` 第二层组件表 | 后台只有两种装饰器形态（表单项/搜索项），它自己也只注册了 `FormItem` 和 `FilterItem` 两个 |
| `dataSourcePolicy` 四策略 | `clear` 和 `filter` 两个分支实现完全一样（`form.ts:117-122`），真正需要的只有一个 |
| `x-layout` void 节点路径上浮 | 让布局参与数据路径计算，三处都要写特殊分支。我们把布局做成纯渲染层，见 [05](05-场景投影.md) |
| 可视化模型构建器（~1000 行 + draft⇄schema 双向映射） | 本期非目标，双向映射是长期 bug 源 |

## 必须自己补的（两个项目都没有）

| 缺失 | 详见 |
|---|---|
| **权限**（页面/行操作/字段/数据四级）。alien-form 业务代码 grep `permission\|rbac\|acl` 零命中，行操作是 42 行硬编码 JSX；Formily 完全不涉及 | [10](10-权限模型.md) |
| **搜索操作符**。alien-form 的 filter 产物是平铺 `{field: value}`，操作符全靠后端约定，**日期区间/金额 between 表达不了**——这是后台刚需 | [05](05-场景投影.md) |
| **Schema 版本管理 + 灰度 + 回滚**。alien-form 服务端只有两个时间戳，无 version、无历史、无并发保护（PUT 整份覆盖） | [12](12-Schema治理.md) |

## 两个项目有意省掉、但我们必须做的

| 项 | 说明 |
|---|---|
| `touched` / `dirty` / `pristine` | alien-form 的 14 个 signal 里没有，导致 `validate()` 一次校验所有字段，**打开新增弹窗什么都没填就全表单飘红**，只能靠「仅 submit 时校验」规避。我们要「离开焦点才校验该字段」 |
| 声明式校验规则 | alien-form 的 `ValidatorFormats` 定义了 email/url/phone/idcard 等 8 种格式但**零实现、零消费方、是死类型**，想表达「长度 2-20」都得写表达式。而我们 99% 的 rules 是三件套，Element Plus 的 async-validator 已免费提供 |

## 会改变这个判断的情况

1. 团队转 React —— `@formily/antd-v5` 生态完整度是另一个世界
2. 需要给业务方嵌入式可视化设计器，且接受在 Vue 里挂 React 壳 —— 那该直接选 amis + amis-editor，而不是 Formily
3. 自研编译器在表单联动/异步选项/数组字段上失控 —— 评估 form-create
