# 10 权限模型

两个参考项目在这块都是空白：alien-form 业务代码 grep `permission|authoriz|rbac|acl` **零命中**（它的 `school-role` 模型里有个 `viewableTables` 字段，注释自称「最朴素的权限存储」，但前端没有任何代码读它）；Formily 完全不涉及权限。

**所以这块要自己设计。好消息是我们的现有机制够用，不需要新造。**

## 1. 现有机制（直接复用）

| 层 | 实现 | 位置 |
|---|---|---|
| 权限码来源 | 后端菜单树里 `type` 为 `A`/`BA` 的节点带 `permission` 字段 | `src/router/utils/parser.ts` 的 `GetPermission()` → `Map<permission, path>` |
| 存储 | `menuStore.setPermissions()` | `src/store/modules/menu.ts` |
| 判定 | `hasPermission(code) => permissions.has(code)` | `src/composables/usePermission.ts` |
| 指令 | `v-permission="'manager:role:add'"`（无权限直接 `removeChild`） | `src/directives/permission.ts` |
| 行操作过滤 | `ArtOperation` 内部按 `item.permission` 过滤 list | 已内置 |
| 页面级 | 菜单未下发 → 路由不注册 | `registerDynamicRoutes` |
| 数据权限（行级） | 后端 `EntityRule.expression` + `roleentity` | 前端只做 CRUD 界面 |

**引擎不引入新的权限体系，只是把权限码放进配置。**

## 2. 四级权限

### ① 页面级

```ts
meta: { auth: 'manager:role:query' }
```

实际上页面级由「菜单是否下发」决定（未下发则路由不注册），`meta.auth` 是**冗余的二次校验**——防止有人直接敲 URL 访问 `/generic/crud?schema=xxx`。

页壳在 mount 时检查：无权限 → 渲染 403 视图，不发任何请求。

### ② 行操作级

```ts
actions: [
  { label: '修改角色', do: 'edit',   auth: 'manager:role:update' },
  { label: '删除角色', do: 'delete', auth: 'manager:role:delete' },
]
toolbar: [{ type: 'create', auth: 'manager:role:add' }]
```

编译成 `OperationItem.permission`，`ArtOperation` 自动过滤（已内置）。工具栏按钮由页壳用 `hasPermission()` 判断。

现有 115 个操作项里 111 个有 `permission`，4 个缺（`manager/app` 授权管理、`manager/feedback` 详细信息、`resource/export` 下载、`resource/file` 复制链接）——**迁移时补上**。

### ③ 字段级（新增能力）

```ts
interface FieldAuth {
  visible?: string | string[]     // 有其中任一权限码才可见
  editable?: string | string[]    // 有其中任一权限码才可编辑，否则只读
}
```

```ts
fields: {
  secret: { label:'密钥', type:'string', 'x-auth': { visible: 'manager:app:secret:view' } },
  status: { label:'状态', type:'boolean', 'x-auth': { editable: 'manager:role:status:update' } },
}
```

三个场景各自的行为：

| 场景 | `visible` 不满足 | `editable` 不满足 |
|---|---|---|
| table | 该列不生成 | 无影响（表格本就只读） |
| search | 该搜索项不生成 | 无影响 |
| form | 该表单项不生成 | 渲染为只读态（等价 `mode='detail'` 的单字段） |

**在编译期过滤，不在渲染期**——理由见 §4。

### ④ 数据级（行级）

不进本协议。数据权限由后端 `EntityRule.expression` 在查询时施加，前端不感知也不该感知。

引擎唯一需要做的：**不因为后端返回的数据少于预期而报错**。

## 3. `statusSwitch` 的权限

现有代码在模板里写：

```vue
<el-switch :disabled="!$hasPermission('manager:role:status:update')" />
```

协议里通过 slot 声明表达：

```ts
'x-table': { slot: { type: 'statusSwitch', auth: 'manager:role:update' } }
```

无权限时开关渲染为 `disabled`，而不是隐藏——用户需要看到当前状态。

## 4. 编译期过滤 vs 运行期过滤

**决策：字段级和列级在编译期过滤，行操作在运行期过滤。**

理由：

| | 编译期过滤 | 运行期过滤 |
|---|---|---|
| 字段/列 | ✅ 权限码在编译时已知（`menuStore` 已加载完），过滤掉可减少后续所有处理 | 每次渲染重复判断 |
| 行操作 | ❌ 因为还要叠加 `hiddenWhen` 的**按行**求值，必须运行期 | ✅ |

**注意时序**：编译必须发生在 `menuStore.setPermissions()` 之后。这在路由守卫链里天然成立（`beforeEach` 里 `processBackendMenu()` 先设置权限再注册路由，页面组件在之后才 mount），但**编译产物缓存的 key 必须包含权限指纹**，否则切换账号后可能命中上一个账号的编译结果。

```ts
const cacheKey = `${schemaId}:${schemaVersion}:${permissionFingerprint}`
```

`permissionFingerprint` 可以是权限码集合的哈希，或直接用 `userStore.id + loginAt`。

## 5. 安全边界（必须写清楚）

**前端权限过滤只是 UX，不是安全边界。**

- 隐藏按钮不等于禁止操作 —— 后端每个接口必须独立鉴权（现有 `menu` 表里 `type='A'/'BA'` 的节点就是 API 权限点，kratos 中间件按此校验）
- 字段级 `visible` 只是不渲染 —— **敏感字段不该出现在列表接口的响应里**。`x-auth.visible` 不能替代后端的字段裁剪（参考 alien-form 后端 `publicRecord()` 删掉 `passwordHash`/`openid` 的做法）
- 配置本身的写权限是一个新的攻击面 —— 谁能改 `page_schema`，就能改所有人看到的页面。见 [12](12-Schema治理.md)

## 6. 配置里权限码的可发现性

配置里手写权限码字符串容易拼错，且拼错的后果是**按钮永久不显示**（`hasPermission` 返回 false），排查困难。

对策：

1. TS 层用字面量联合类型收窄（可从菜单接口生成 `.d.ts`，本期不做，先用 `string`）
2. **开发环境下，编译期把配置里所有 `auth` 码与 `menuStore.permissions` 比对，不存在的进警告通道**（不是错误——权限码可能对当前账号不适用）
3. 配置界面（未来）从菜单树里选权限码，不手输
