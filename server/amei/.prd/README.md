# amei 分发助手技术方案

> 状态：方案设计，待平台权限与账号实测确认
> 日期：2026-11-12
> 目标：把书籍简介、书评、图文和短视频通过平台官方开放能力分发，并回流内容数据
> 原则：只从官方开放平台 API 发布；GitHub 开源实现先调研再决定复用；不做网站页面/Cookie/逆向发布

## 1. 结论

amei 按三层拆分，不做成一个巨型服务：

| 层 | 仓库/目录 | 职责 |
| --- | --- | --- |
| 控制面 | `amei` | 手机号用户、内容版本、平台账号索引、批量发布、调度、数据汇总、后台 |
| 媒体层 | `amei-media` | 上传接收、媒体校验、转码、封面、字幕、对象存储、签名下载 URL |
| 平台适配层 | `amei-adapters` | 平台 OAuth、凭据加密与续期、平台素材上传、字段映射、发布、状态、数据拉取 |

上层只认统一内容和统一任务协议；平台差异全部留在适配器。一个“一键发布”会拆成
`contentVersion × platformAccount` 的多个独立任务，各平台独立推进、重试和人工接管。

## 2. 关键边界

- amei 用户手机号注册/登录属于控制面能力，短信通道可插拔，不把短信供应商写死。
- 平台登录属于适配器能力。控制面发起统一 OAuth/授权挑战，不保存平台密码、cookie、access token 或 refresh token。
- 抖音、快手、B 站、微博、小红书、视频号均按开放平台能力建设；没有确认真实发布 API 的平台默认禁用自动发布。
- 本期明确不做创作者网页后台自动化，不保存 Cookie、storage state 或网页登录态；没有开放 API 的平台只做能力占位和人工任务。
- 媒体上传与平台发布分开建模。视频先进入 `amei-media`，适配器再把签名 URL 对应的素材上传到平台并取得平台素材 ID。
- 平台额度、应用权限和接口限流分开记录；不把内部软限制写成平台官方额度。

## 3. 六个平台的首轮结论

| 平台 | 官方内容发布能力 | GitHub 复用结论 | 首轮策略 |
| --- | --- | --- | --- |
| 抖音 | 视频、图文、作品数据接口已在官方 SDK 中核实 | `bytedance/douyin-openapi-sdk-go`，Apache-2.0，直接复用 | 第一优先实现 |
| 快手 | 社区 SDK 有完整视频链，但版本较旧，官方文档需复核 | `bububa/kwai-openapi`，Apache-2.0，仅作参考 | 第二优先，沙箱/测试应用验证后启用 |
| B 站 | 官方 demo 已核实授权码换 token、视频分片上传、封面、分区和投稿；鉴权方式需实测 | 官方 demo 已归档且无 License，仅参考；`biliup` 禁止商用；`biligo` 仅直播 | 申请权限并用测试应用确认鉴权后开启 |
| 微博 | 文本/图片分享接口已核实；视频只对政务、媒体、机构开放 | `axiaoxin-com/weibo` 可参考 OAuth 和文本接口 | 先做文本/图片，视频按机构资质单独开通 |
| 小红书 | 开放平台导航只有电商类 API，未发现内容发布 API | 未找到可信可复用实现 | 默认禁用自动发布，继续申请/确认 |
| 视频号 | 官方文档只确认小店能力，未发现公开视频发布 API | 未找到可信可复用实现 | 默认禁用自动发布，禁止爬取/逆向 |

平台额度的公开可核实信息很少。当前只确认 B 站“非正式会员单日最多投递 5 个稿件”；
其他平台的真实发文额度标记为 `未核实/待补充`，不填运营估算冒充官方规则。

## 5. 事实标记

本目录统一使用以下验证状态，避免把推测写成事实：

| 状态 | 含义 |
| --- | --- |
| `已核实` | 已查看官方文档、官方 SDK 或官方仓库，并记录 URL/版本 |
| `登录后可见/待验证` | 入口存在，但关键字段、权限或流程需要登录开发者后台确认 |
| `仅应用内操作` | 只能由平台 App 或后台人工完成，服务端无法直接代操作 |
| `无公开 API` | 当前未找到公开的内容发布接口 |
| `未核实/待补充` | 信息不足，禁止据此承诺自动能力 |
