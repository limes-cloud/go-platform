# 发布额度与限流

> 状态：证据清单 / 方案约束
> 日期：2026-11-12
> 原则：未知额度不填估算值；平台官方额度、应用配额和 amei 内部软额度分开计算
> 结论：目前仅 B 站非正式会员的“单日 5 个稿件”可公开核实

## 1. 三类限制不能混为一谈

| 类型 | 由谁决定 | 示例 | 能否由产品修改 |
| --- | --- | --- | --- |
| 平台官方内容额度 | 内容平台 | B 站非正式会员单日 5 个稿件 | 否 |
| 应用/API 配额 | 开放平台应用 | 每日接口调用量、QPS、并发上传数 | 只能申请，不能绕过 |
| amei 内部软额度 | 产品 | 新账号每日先发 1 篇、单批次最多 10 个账号 | 是 |

产品界面必须分别展示，不能把 amei 的软限制写成“平台只允许 1 篇/天”。

## 2. 公开可核实额度

| 平台 | 内容类型 | 公开额度/限流 | 证据状态 |
| --- | --- | --- | --- |
| 抖音 | 视频/图文 | 每日发布额度、应用配额、QPS 均未核实 | 登录开发者后台确认 |
| 快手 | 视频 | 每日发布额度、应用配额、QPS 均未核实 | 官方文档登录后复核 |
| B 站 | 视频稿件 | 非正式会员单日最多投递 5 个稿件；正式会员规则以后台为准 | 已核实 |
| 微博 | 文本/图片 | 有接口频次限制，具体数值未核实；高级接口需额外权限 | 部分核实 |
| 微博 | 视频 | 仅政务、媒体、机构等实体可申请，个人暂不能接入 | 已核实范围限制，额度未知 |
| 小红书 | 笔记/视频 | 未发现内容发布 API，额度不适用 | 无公开 API/未核实 |
| 视频号 | 视频/图文 | 未发现公开内容发布 API，额度不适用 | 无公开 API/未核实 |

B 站证据来自服务端稿件提交文档：

```text
POST https://member.bilibili.com/arcopen/fn/archive/add-by-utoken
非正式会员单日最多投递 5 个稿件；
可在主站通过答题转为正式会员解除限制。
```

“正式会员解除限制”不等于无限量，也不等于应用 API 没有 QPS 限制。正式会员的真实规则和接口配额仍以后台为准。

## 3. 应用级配额

以下项目必须登录开发者后台逐一确认，不能从 GitHub SDK 推断：

- 是否有内容发布接口权限；
- 每日接口调用上限；
- 单接口 QPS；
- 单用户/单账号调用上限；
- 素材上传并发和单文件大小；
- 审核状态查询频率；
- 数据接口的历史回溯范围和分页上限；
- 测试应用与生产应用的差异。

适配器能力响应建议：

```json
{
  "quotaSources": {
    "platformDailyLimit": 5,
    "platformLimitStatus": "已核实",
    "platformLimitScope": "非正式会员视频稿件",
    "appDailyQuota": null,
    "appQps": null,
    "rateLimitHeaders": [],
    "verifiedAt": "2026-11-12"
  }
}
```

未知字段统一为 `null`，并让前端展示“以后台为准”，不能默认填 0 或 9999。

## 4. 本地软额度

本地软额度用于保护新账号、控制成本和降低审核风险，不是平台规则。建议配置：

| 配置 | 默认建议 | 说明 |
| --- | --- | --- |
| `newAccountDailyLimit` | 1 | 新绑定的平台账号首日最多 1 个任务 |
| `accountDailyLimit` | 3 | 稳定账号的保守上限，可按平台覆盖 |
| `batchAccountLimit` | 10 | 单批次最多选择的平台账号数 |
| `perPlatformConcurrentUploads` | 1–2 | 避免大视频并发打满出口 |
| `maxRetryPerTask` | 3 | 超过后进入人工接管 |
| `scheduleJitterSeconds` | 30–120 | 避免同一时刻集中提交 |

这些值是产品默认值，不是平台官方额度；上线后根据真实审核结果、账号权重和平台反馈调整。

## 5. 额度计算口径

### 5.1 平台额度

- 以平台返回的成功受理为准，不以“用户点击发布”计数；
- 审核拒绝是否消耗额度以平台规则为准，未知时不自行恢复配额；
- 删除作品是否返还额度未知，不能假设；
- 同一内容多平台分发按平台分别计数；
- 多账号不能用于规避单账号限制。

### 5.2 内部软额度

- 按 `user_id + platform_account_id + stat_date` 计数；
- 只统计已进入 `publishing` 或 `pending_review` 的任务；
- 失败在素材校验阶段的请求不计入平台额度，但计入内部防刷次数；
- 定时任务在触发时再次校验额度；
- 管理员调整软额度必须写审计日志。

### 5.3 未知值

平台没有公开额度时：

- `platformDailyLimit=null`；
- `platformLimitStatus=未核实/待补充`；
- 前端显示“平台未公开每日额度，实际以开发者后台/平台返回为准”；
- 不展示“还剩 N 条”，除非拿到了真实计数来源。

## 6. 限流响应

适配器统一映射：

| 内部错误 | 场景 | 控制面动作 |
| --- | --- | --- |
| `PLATFORM_RATE_LIMITED` | 平台 QPS/日额度触发 | 读取 `retryAfterMs`，延迟重试 |
| `APP_QUOTA_EXCEEDED` | 应用配额耗尽 | 暂停该平台任务，告警人工处理 |
| `ACCOUNT_QUOTA_EXCEEDED` | 账号日额度耗尽 | 将剩余任务排到下一可用窗口 |
| `UPLOAD_CONCURRENCY_EXCEEDED` | 上传并发过高 | 降低并发，保留断点 |
| `PERMISSION_DENIED` | scope 或应用权限不足 | 标记 `needs_action`，要求补权限 |

不允许通过代理、多账号、频繁重试或换 IP 绕过平台限流。

## 7. 调度策略

```text
创建批次
  -> 校验内部软额度
  -> 校验账号能力和平台已知额度
  -> 按账号拆分任务
  -> 平台级并发队列
  -> 遇到限流读取 retryAfter
  -> 超过重试上限进入 needs_action
  -> 单平台失败不阻塞其他平台
```

建议为每个平台维护独立令牌桶；平台没有公开 QPS 时，使用保守并发并通过真实 429/错误码动态降速。

## 8. 展示文案

| 场景 | 文案 |
| --- | --- |
| B 站非正式会员 | 非正式会员单日最多 5 个稿件，正式会员规则以后台为准 |
| 未知平台额度 | 平台未公开每日发布额度，提交后以平台审核结果为准 |
| 应用配额未知 | 当前应用未确认接口配额，请先在开发者后台核对 |
| 权限不足 | 当前开放平台应用未获得该发布能力，请补充权限 |
| 内部软额度 | 今日已达到 amei 安全发布上限，可调整计划或等待次日 |

## 9. 验收

- 没有把未知额度写成固定数字；
- B 站 5 条/日能显示来源和会员条件；
- 平台额度、应用配额、内部软额度分字段存储；
- 429/限额错误可以区分并延迟，不会无限重试；
- 批量发布不会因一个平台额度耗尽而让整批失败；
- 不提供绕过平台限流的功能。
